### 3. HIGH — `IErrorLogger.GetErrorLogsAsync` returns mutable `List<T>`
**Location:** `Interfaces/ErrorLogger/IErrorLogger.cs`

**Issue:** The interface contract returns `List<ErrorLog>`, exposing a mutable collection from a public API. Callers can `Add`/`Remove` entries from what is meant to be a read-only query result.

**Why it matters:** Breaks encapsulation on a public library interface; any future backing store change (DB, stream) would force a breaking change.

**Fix:** Change return type to `IReadOnlyList<ErrorLog>` on both the interface and `ErrorLogger` implementation.

---

### 4. MEDIUM — `ConfirmFieldName` on `ErrorContext` is a MediaVault-specific concept
**Location:** `ResultPattern/ErrorContext.cs`, `ResultPattern/ValidatorExtensions.cs`

**Issue:** `ErrorContext` has a `ConfirmFieldName` constructor parameter used only by `DoesNotMatch` for password-confirmation field pairing. This is a MediaVault-specific auth concept. SharedKernel now has implicit knowledge of a "confirm password" use case.

**Why it matters:** Violates the "must remain MediaVault-agnostic" rule for SharedKernel. Another consumer of the library would have no idea what `ConfirmFieldName` means.

**Fix option A (recommended):** Remove `ConfirmFieldName` from `ErrorContext`. Callers who need to compare two fields pass both field names explicitly to `DoesNotMatch`. The method signature becomes:
```csharp
DoesNotMatch(this string value1, string value2, string fieldName, string confirmFieldName, ErrorContext errorContext, ...)
```
`DoesNotMatch` itself could also be moved out of SharedKernel entirely since it is application-level behaviour.

**Fix option B:** Keep it but rename to something generic like `SecondaryFieldName`.

---

### 5. MEDIUM — `CloneErrorContext` in `HttpResponseToResultExtensions` is fragile
**Location:** `ResultPattern/HttpResponseToResultExtensions.cs`

**Issue:** `CloneErrorContext` manually re-passes every `ErrorContext` constructor parameter. Since `ErrorContext` is a `record`, `errorContext with { }` produces an identical shallow copy. The manual version will silently miss any property added to `ErrorContext` in the future.

**Why it matters:** Maintenance trap — a new property on `ErrorContext` will appear to work but the cloned context will carry a stale/default value.

**Fix:** Replace the entire `CloneErrorContext` method and its call sites with `errorContext with { }` directly, then delete the private method.

---

### 6. MEDIUM — `Cancelled` error type maps to HTTP 500
**Location:** `ResultPattern/HttpResultMapper.cs`

**Issue:** In `BuildFailureResponse`, `ErrorType.Cancelled` maps to `(500, ...)`. A cancelled operation is not a server fault — it is typically caused by the client disconnecting or a request timeout.

**Why it matters:** Callers see a server error when the real cause was a timeout or cancellation. Harder to distinguish from genuine failures in logs and monitoring.

**Fix:** Map `Cancelled` to 503 (Service Unavailable) or 504 (Gateway Timeout). At minimum, add a comment explaining why 500 was chosen if it is intentional.

---

### 7. MEDIUM — `Validator.ValidateAndAdjustPaginationParameters` uses `ref` and has no max cap
**Location:** `ResultPattern/Validator.cs`

**Issue:** The `ref`-based API is unidiomatic for a public library — callers must declare mutable locals. There is also no maximum `pageSize` clamp, so `pageSize = 10_000` is silently accepted.

**Why it matters:** `ref` parameters are awkward at call sites. The missing max cap is a potential performance/DoS concern if callers pass unbounded page sizes.

**Fix:** Consider a `record PaginationParameters(int PageNumber, int PageSize)` with a static `Normalize(int pageNumber, int pageSize, int maxPageSize = 100)` returning a normalised instance.

---

### 8. LOW — `ErrorContext.FullDescription` appears unused in the library
**Location:** `ResultPattern/ErrorContext.cs`

**Issue:** `FullDescription` is a computed property but has no call sites within SharedKernel itself. It may be dead code, or it is only consumed directly by MediaVault.

**Fix:** If unused, remove it to reduce public API surface. If used in MediaVault, add a `<summary>` and keep it.

---

### 9. LOW — `ErrorLogger.TryDeserializeLog` swallows all exceptions silently
**Location:** `ResultPattern/ErrorLogger.cs`

**Issue:** The catch block returns `null` with no tracing. A corrupted NDJSON entry is silently dropped.

**Fix:** Add a `Debug.WriteLine` at minimum, or accept a diagnostics delegate. Silent drop is acceptable in production but impossible to diagnose locally.

---

### 10. LOW — `HasJsonContentType` treats absent Content-Type as JSON-compatible (undocumented)
**Location:** `ResultPattern/HttpResponseToResultExtensions.cs`

**Issue:** If `mediaType` is null/whitespace, the method returns `true` and proceeds to deserialise. The intent is to be lenient with APIs that omit the content-type header, but this assumption is invisible to callers.

**Fix:** Add a `<remarks>` XML doc explaining the leniency policy, or return `false` and handle the no-content-type case explicitly in the calling path.

---

### 11. LOW — `ValidationErrorResponseBody` exposes only error codes, not descriptions
**Location:** `ResultPattern/MappedHttpResponse.cs`, `ResultPattern/HttpResultMapper.cs`

**Issue:** The validation error body sends `validationErrors.Select(x => x.Code)` — clients receive `Create.User.Required` rather than a human-readable description. This may be intentional to avoid leaking internals, but it is undocumented.

**Fix:** Document the design decision. If descriptions should also reach clients, add `IEnumerable<string>? ValidationErrorDescriptions` to `ValidationErrorResponseBody`.

---

### 12. LOW — Missing XML docs on several public types
**Files:** `ErrorContext`, `ErrorCode`, `DatabaseError`, `HttpError`, `ErrorLogPolicy`, `ValidatorExtensions` (partial), `ErrorReasonCode` enum, `OperationType` enum.

For a NuGet-publishable library, public types without `<summary>` show as empty in IDE tooltips.

## Open questions

1. Is `DoesNotMatch` expected to stay in SharedKernel long-term, or move to MediaVault once `ConfirmFieldName` is resolved?
2. Is `ErrorContext.FullDescription` consumed anywhere in MediaVault? If not, it is dead API surface.
3. Is the `Cancelled → 500` mapping intentional? Was 503/504 considered and rejected?
4. Is the `ValidationErrorResponseBody` codes-only design documented anywhere as a security decision?

## Tests reviewed

The test suite is solid for the happy and sad paths of `Result`, `Result<T>`, `ResultExtensions`, `HttpResultMapper`, `ValidatorExtensions`, `IsValidId`, and pagination.

**Gaps:**
- No test for `ErrorLogger` under concurrent access (the race condition in finding #1 has no regression test)
- No test for `ErrorType.None` reaching `HttpResultMapper.MapFailure` (the `_` fallback maps to 400)
- `DoesNotMatch` has no test for the case where both arguments are null simultaneously
- No test verifying `CloneErrorContext` preserves all fields (would catch a future regression on finding #5)

---

## Residual risk

The `ErrorLogger` concurrency issue (#1) is the only finding that can produce **silent data loss** in production. Everything else is API design debt or correctness nits that won't cause runtime failures under normal use. The NRT issue on `IsNullOrWhiteSpace` (#2) is the most likely to cause friction when adding new validators in MediaVault.
